# StaleZero World-Class Developer Feature Plan
Generated for: KirtiRamchandani/StaleZero
Purpose: Give Cursor a complete, start-to-finish implementation brief for turning StaleZero into a highly useful, trusted, production-grade, widely adopted developer tool.

================================================================================
0. NORTH STAR
================================================================================

StaleZero should become the standard TypeScript mutation-consequence engine:
when data changes, every cache, state store, view, queue, search index, websocket client,
analytics event, edge cache, and downstream system receives the correct invalidation or sync
action with proof, observability, safety, and developer confidence.

The project should feel like:
- "React Query Devtools + OpenTelemetry + cache invalidation graph + receipts + workflows"
- "Terraform plan/apply, but for application state and cache consequences"
- "Stripe-grade DX for mutation side effects"
- "A production safety layer around stale data"

Core promise:
Developers declare the mutation once, preview the blast radius, execute it safely,
prove the result, and get an audit receipt.

================================================================================
1. PRODUCT POSITIONING
================================================================================

1.1 One-line positioning
StaleZero is a TypeScript engine for declaring, previewing, executing, proving, and observing every cache/state/index/client consequence of a data mutation.

1.2 Target users
- Full-stack TypeScript teams
- SaaS teams with Redis, Next.js, React Query, SWR, Redux, Zustand, search, queues, and websockets
- Teams suffering stale UI, stale cache, missed revalidations, broken invalidation rules, and invisible mutation side effects
- Platform teams that want consistency, auditability, and governance across services

1.3 Primary use cases
- Invalidate Redis keys after DB mutations
- Revalidate Next.js tags/paths
- Invalidate React Query/SWR/tRPC/Apollo client state
- Notify websocket rooms
- Enqueue search reindex jobs
- Emit outbox/events for downstream services
- Preview what will be affected before execution
- Store receipts for debugging and compliance
- Prove that important targets were actually updated
- Build devtools around mutation graphs
- Detect stale-data drift

1.4 Make it famous by being:
- Dead simple in the first 5 minutes
- Deeply trustworthy in production
- Visually impressive with graph/devtools
- Compatible with every popular TypeScript stack
- Safe by default
- Extremely well tested
- Fun to demo

3. CORE API FEATURES
================================================================================

3.1 createStaleZero()
Subfeatures:
- createStaleZero(config)
- createStaleZero.production(config)
- createStaleZero.dev(config)
- createStaleZero.test(config)
- Environment-specific defaults
- Helpful warnings for unsafe defaults
- Optional strict mode

Required changes:
- Add mode presets:
  - "development"
  - "test"
  - "production"
- Production defaults should be safe:
  - no in-memory receipt store without warning or explicit allow
  - security.blockUnsafeTargets true
  - unknown mutations rejected unless explicitly allowed
  - devtools disabled unless auth configured
- Add config validation with clear error messages.

Acceptance criteria:
- A new developer can create an instance with one line.
- Production config cannot silently expose dangerous behavior.

3.2 Mutation declarations
Current concept:
stale.mutation("UserUpdated", { schema, affects, targets, fields, routes, owner })

Desired subfeatures:
- Strong type inference from schemas
- Support Zod, Valibot, ArkType, Effect Schema, TypeBox, Standard Schema
- Required/optional mutation owners
- Tags and metadata
- Mutation descriptions
- Examples in generated docs
- Deprecation flags
- Versioning
- Risk classification
- Required approval policy
- Tenant policy
- Idempotency policy
- Replay policy
- Changelog for mutation graph changes

Suggested API:
stale.mutation("UserUpdated", {
  description: "Runs after a user profile update",
  owner: "platform",
  schema: UserUpdatedSchema,
  affects: input => [entity("User", input.userId)],
  targets: input => [
    redisTarget(`user:${input.userId}`),
    queryTarget(["user", input.userId]),
  ],
  policy: {
    strict: true,
    requireActor: true,
    idempotent: true,
    maxTargets: 20,
  }
})

Acceptance criteria:
- Undeclared mutation behavior is configurable:
  - default production: reject
  - development: warn
  - explicit allow: allowUndeclaredMutations true
- Mutation registration should validate duplicate names.

4. ENGINE EXECUTION FEATURES
================================================================================

4.1 Execution pipeline
Current pipeline:
parse -> affected -> context -> targets -> risk -> guard -> execute -> publish -> prove -> receipt -> audit -> notify.

Desired changes:
- Make this pipeline explicit and modular.
- Add lifecycle hooks:
  - beforeParse
  - afterParse
  - beforePreview
  - afterPreview
  - beforeGuard
  - afterGuard
  - beforeExecute
  - afterTarget
  - afterExecute
  - beforeReceipt
  - afterReceipt
  - onFailure
- Add pipeline tracing.
- Add cancellation via AbortSignal.
- Add deterministic execution IDs.
- Add execution plans.

Acceptance criteria:
- Each stage is independently tested.
- Each stage can be traced and debugged.

4.2 Timeouts and cancellation
Current timeout uses Promise.race but cannot force-cancel an adapter unless the adapter cooperates.

Desired subfeatures:
- Pass AbortSignal in MutationContext.
- Adapter contract should support context.signal.
- withTimeout should abort the signal.
- HTTP adapter should use signal.
- Redis/search/queue adapters should respect signal when possible.
- Receipt should mark timeout separately from generic failure.

Acceptance criteria:
- Timed-out HTTP target actually aborts fetch.
- Receipt records status: failed, error.name: TimeoutError.

4.3 Retry behavior
Subfeatures:
- Per-target retry config
- Per-adapter retry config
- Global retry config
- Retry backoff
- Retry jitter
- Retry only on retryable errors
- Retry budgets
- Retry hooks
- Retry reasons in receipts
- Test deterministic retry timing

Acceptance criteria:
- Retried target receipt shows attempts, delays, and final reason.

4.4 Circuit breaker
Subfeatures:
- Per-adapter circuit breaker
- Per-target group circuit breaker
- Half-open state
- Reset on success
- Manual reset API
- Circuit state in health
- Circuit events in audit log

Acceptance criteria:
- Circuit opens after configured threshold.
- Circuit half-opens after cooldown and closes on success.

4.5 Concurrency
Subfeatures:
- Global concurrency
- Adapter concurrency
- Lane-based concurrency
- Priority queues
- Required targets first
- Optional targets later
- Background execution for optional targets, if configured
- Deterministic ordering in receipts

Acceptance criteria:
- Required target failures are always visible.
- Optional target failures can be non-blocking but still recorded.

4.6 Batching
Current batchExecute returns void, which cannot represent partial success.

Required change:
- Update Adapter.batchExecute to optionally return per-target results.

Suggested contract:
batchExecute?: (
  targets: Target[],
  context: MutationContext
) => MaybePromise<void | Array<{
  target: Target
  status: "success" | "failed" | "skipped"
  error?: unknown
  message?: string
}>>

Subfeatures:
- Batch fallback to single execution
- Batch result normalization
- Partial batch failures
- Batch size limits
- Batch grouping by adapter/action/lane/priority
- Batch metrics

Acceptance criteria:
- A batch with 10 targets can show 8 success and 2 failed.

4.7 Idempotency
Subfeatures:
- Idempotency key generation
- Idempotency key validation
- Idempotency store interface
- Replay-safe targets
- Duplicate event detection
- Dedupe windows
- Idempotent adapter helpers
- Idempotency conflict detection

Acceptance criteria:

4.8 Dry-run and preview

5. SAFETY AND SECURITY FEATURES
================================================================================

5.1 Safe by default
Required changes:
- Production mode should default to:
  - security.blockUnsafeTargets true
  - require HTTPS for HTTP targets
  - block private IPs and localhost
  - block Redis wildcard deletes
  - block pattern deletes unless allowlisted
  - reject unknown mutations
  - warn if no durable receipt store
  - devtools disabled
  - no unsafe CORS

Acceptance criteria:
- Unsafe HTTP and Redis targets are blocked without needing advanced config.

5.2 HTTP adapter security
Current risk:
HTTP adapter directly fetches target.key. Engine has checks, but adapter does not enforce them itself.

Required changes:
- Move baseline SSRF checks into HTTP adapter:
  - requireHttps default true
  - block localhost default true
  - block private IP literals default true
  - block metadata IP 169.254.169.254
  - allowHosts support
  - denyHosts support
  - allowedMethods
  - maxBodyBytes
  - maxResponseBytes
  - no redirect to private hosts
  - DNS rebinding mitigation if possible
- Add signed webhook helpers:
  - HMAC sha256
  - timestamp header
  - replay window
  - verify function for receivers

Acceptance criteria:
- HTTP adapter is safe even if engine security config is forgotten.

5.3 Redis safety
Subfeatures:
- Pattern delete allowlists
- Prefix allowlists
- Max keys per pattern
- Dry-run scan before delete
- Chunked deletes
- UNLINK default option
- Audit record of deleted key count, not raw keys if sensitive
- Protect production broad deletes
- Require approval for broad deletes

Acceptance criteria:
- `redisPatternTarget("*")` is impossible in production without explicit unsafe override.

5.4 Devtools security
Required changes:
- If enabledInProduction is true, require auth function unless explicitly allowUnauthenticatedInProduction is true.
- Strong CORS defaults.
- Redaction always applied before UI.
- Hide receipt payload by default in production.
- Add "safe share" mode that strips payloads and target secrets.
- Add CSP headers.
- Add no-store cache headers.
- Add rate limiting for preview endpoint.

Acceptance criteria:
- Production devtools cannot be accidentally exposed with full receipts.

5.5 Redaction
Subfeatures:
- Redact by key name
- Redact by path
- Redact by regex
- Redact by schema metadata
- Redact by value detector:
  - email
  - token
  - JWT
  - API key
  - credit card
  - phone
- Redaction preview
- Redaction tests
- Redacted marker metadata
- Custom redaction function
- Irreversible redaction for receipts

Acceptance criteria:
- Sensitive values never appear in stored receipts, devtools, logs, or notifications.

5.6 Multi-tenant safety
Subfeatures:
- Tenant resolver for actor
- Tenant resolver for input
- Tenant resolver for targets
- Cross-tenant block by default
- Tenant allowlists
- Tenant-scoped receipts
- Tenant-scoped devtools view
- Tenant proof
- Tenant-aware rate limits

Acceptance criteria:
- A mutation from tenant A cannot target tenant B unless explicitly allowed.

5.7 Approval gates
Subfeatures:
- Require approval by mutation
- Require approval by risk
- Require approval by target count

- Require approval by tenant
- Approval token verification

Acceptance criteria:

- Core has high unit coverage.

- Integration tests cover real-world stacks.
- Security-sensitive behavior is safe by default.

Production readiness:
- Durable receipt stores exist.
- Devtools are safe in production.

- CI catches graph/API/security regressions.
- Receipts are queryable and useful.

- Community can build adapters easily.
